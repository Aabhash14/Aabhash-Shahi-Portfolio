About me

Started as a QA intern in 2023 and progressed to owning the company’s end-to-end quality function, becoming the sole QA engineer supporting nine developers across multiple De Heus products. Established QA processes from the ground up where no formal testing infrastructure existed, including test plans, test case repositories, defect workflows, and systematic testing for previously untested applications.

Built the company’s QA practice from the ground up, establishing the QA standards the team works to, along with a centralised test case library in Azure DevOps. Designed and integrated a Playwright automation suite into Azure Pipelines for continuous CI/CD execution, turning automated regression from on-demand testing into an ongoing quality gate. Developed an AI-powered documentation agent that generates technical and functional documentation from the codebase. These systems are designed for long-term quality ownership: maintainable automation, reusable documentation and clear stakeholder reporting that stay effective beyond any one contributor.

Quality process

ImpactEvery backlog app brought under coverage

Case studyClose

There was no QA process to inherit. I wrote the one the team still works to.

The problem

When I moved from intern to trainee, testing at Proshore was ad hoc: no test plans, no case repository, no entry or exit criteria, no defect workflow. There was also a backlog of applications that had never been systematically tested at all.

My role

Authored the standards and worked the backlog down application by application.

Challenges

Standards only work if the team uses them, and a process written by one person is easy to ignore. Keeping it light enough to follow, and applying it visibly to my own work first, is what got it adopted.

Approach
  • Write the standard first, then apply it; otherwise every project invents its own.
  • Work the untested backlog application by application rather than sampling across all of them.
  • Prioritise by risk: pricing, contracts and access control before anything cosmetic.
How it works
  • Test case library established in Azure DevOps, giving the first traceable record of coverage.
  • Test plans, entry and exit criteria, and severity definitions documented as team standards.
  • Defect workflow defined from report through to verified closure.
  • Automation introduced against the standard, so generated and hand-written cases follow the same structure.
Results
  • Every backlog application brought under documented coverage.
  • Entry and exit criteria and a defect workflow the whole team works to.

Playwright in continuous regression

Introduced Playwright in 2023 and wired it into Azure Pipelines with JUnit and HTML reporting, so regression runs after every commit rather than whenever there was time for a manual pass.

Automation framework

ImpactRegression on every commit, not on request

Case studyClose
The problem

Regression was manual and therefore rationed: it happened when there was time, which meant it happened late. With four products and one tester, a manual full pass was never going to fit inside a sprint.

My role

Proposed, built and own the framework.

Challenges

Flaky specs undermine an automated suite faster than missing coverage does. Stabilising waits and authentication state, and triaging flake as its own class of defect, was most of the real work after the first version shipped.

Approach
  • Automate the paths that get run every release first, not the ones that are easiest to automate.
  • Structure for maintenance from the start; a suite nobody can edit is a suite that gets deleted.
  • Run on every commit so failures surface next to the change that caused them.
How it works
  • Playwright suite built on the Page Object Model with reusable authentication state.
  • Cross-browser execution across the products in scope.
  • Azure Pipelines integration publishing JUnit and HTML results per run.
  • Shared login module, so an authentication change is one edit, not one per product.
Results
  • Regression now runs on every commit instead of on request.

  4. JUnit + HTML
  5. Sign-off

Agentic AI workflow

ImpactManual copy-paste removed from the QA cycle

Case studyClose

A workflow that takes a feature and returns a filed bug ticket, with no manual handoff between steps.

The problem

As the only QA engineer across four products, every step of the cycle was a separate manual job: write the cases, write the scripts, run them, read the failures, write the bug report, raise the ticket. Each handoff cost time, and each one was a place work stalled when I was pulled onto something else.

My role

Sole designer and implementer, alongside my regular QA responsibilities.

Challenges

A wrong generated case is worse than no case, because it creates false confidence. Constraining generation to observed application state, and reviewing every batch before it lands, is what made the output trustworthy. Duplicate tickets were the other risk: an automated reporter that files the same bug twice loses the team’s trust immediately.

Approach
  • Treat the QA cycle as one pipeline rather than six tasks.
  • Keep a human approval gate before anything reaches Azure DevOps.
  • Generate into the team’s existing system of record, so nothing lives in a side channel.
How it works
  • Test cases generated from the application under test rather than written by hand.
  • Executable scripts generated from those cases, structured on the Page Object Model so they stay maintainable.
  • Execution, then failure triage on the results.
  • Bug report drafted from the failure, and the ticket raised in Azure DevOps, in the same flow.
Results
  • Manual copy-paste transfer removed from the cycle entirely.

Documentation Agent

A Claude Code workspace that documents any codebase. It reads the code and produces both registers of documentation: technical detail for developers and a functional description for the client.

AI documentation agent

ImpactDocs refreshed on change, not rewritten

Case studyClose

Documentation that used to be written by hand for every project, produced from the codebase instead.

The problem

Four products meant four sets of documentation, technical and functional, and documentation is the first thing to fall behind when one person covers everything. Out-of-date docs are worse than none, because people still trust them.

My role

Built and maintain the agent.

Challenges

Generated documentation drifts toward describing code rather than explaining behaviour. Getting the functional register right, written for someone who does not read the repository, took more iteration than the technical one.

Approach
  • Generate from the source of truth, the codebase and the application itself, not from memory.
  • Produce both registers: technical detail for developers, functional description for the client.
  • Make regeneration cheap, so docs can be refreshed rather than rewritten.
How it works
  • The agent reads the codebase and produces structured technical documentation.
  • Functional documentation generated for client-facing use from the same pass.
  • Output published to the project wiki alongside the rest of the project record.
  • Templates keep structure consistent across all four products.
Results
  • Docs now refreshed on change instead of going stale between releases.

API test automation in Postman

Moved API coverage from a folder of saved requests someone had to click through to an automated suite asserting on contract, payload and error paths, with SQL verification behind it.

API automation

ImpactContract defects caught before the UI

Case studyClose

Moving API testing from manual request checks to an automated suite that runs with the rest of the pipeline.

The problem

API coverage existed as a folder of saved requests that someone had to click through. It only got exercised when a person remembered to do it, which meant contract and validation regressions reached the UI before anyone noticed.

My role

Built the automated API coverage across the products in scope.

Challenges

Test data. API assertions are only as good as the state they run against, so building repeatable data setup mattered more than the assertions themselves.

Approach
  • Assert on contract, not just on status codes: shape and payload as well as 200.
  • Cover the error paths, since that is where API behaviour actually diverges.
  • Automate execution so coverage does not depend on someone remembering.
How it works
  • Postman collections built out across CRUD, status-code and error-path coverage.
  • Response schema and payload assertions rather than status checks alone.
  • Database verification in SQL behind the API, confirming what was written matched what was returned.
  • Automated execution so API regression runs alongside UI regression.
Results
  • API regression now runs automatically rather than on demand.
  • Contract and validation defects caught before reaching the interface.
Flow
  1. Request
  2. Status + schema
  3. Payload
  4. SQL check
  5. Report
